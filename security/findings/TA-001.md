# TA-001 — Protocol activity leaks through frame count

**Status:** OPEN
**Severity:** Privacy / traffic-analysis
**Affected revision:** `789bede` (present since the transport was written)
**Class:** metadata leakage. **Not** a cryptographic defect.

## Observer capability assumed

Frame sizes, frame counts and timing on a single link. No plaintext, no keys,
no decryption. Everything a passive network observer sees.

## Result

240 samples, 4 activity classes, stratified 5-fold CV over 5 seeds:

| feature set | accuracy | 95% CI |
|---|---:|---|
| per-frame SIZE only | 50.0% | ±0.0 |
| SIZE + COUNT | 75.0% | ±0.0 |
| SIZE + COUNT + TIMING | 74.1% | ±2.1 |
| TIMING only | 67.7% | ±1.9 |
| **COUNT only** | **75.0%** | **±0.0** |
| random baseline | 25.0% | — |

## Where the leakage actually is

**Frame count, and only frame count.** Count alone reaches 75.0%, which is the
theoretical ceiling for three distinguishable groups (0 frames / 1 frame /
3 frames) over four balanced classes. Adding timing does not improve on it
(74.1%), so timing is *correlated with* count rather than an independent
channel.

The 50.0% for size-only is likewise the ceiling for two groups, and arises
solely because IDLE transmits **zero** frames. That is a count property, not a
size property.

**Per-frame size leaks nothing.** Every class that transmits emits identical
1084-byte frames. A 16 B and a 600 B payload are indistinguishable at 53.3%
(chance), with Cohen's d = 0.000 on `total_bytes` — a 37x payload difference
is not recoverable. The constant-size envelope does exactly its job.

## Impact

An observer can infer *whether and how much* the protocol is active — idle vs
one message vs a burst — without breaking any cryptography. It does not reveal
payload contents, payload size, hop index, or any stable identifier.

## What this does NOT affect

HKDF-SHA256, X25519, ChaCha20-Poly1305, onion layering, per-hop key
separation, authentication, replay protection and forward secrecy are all
unaffected. Confidentiality holds; traffic-analysis resistance is insufficient.

## Reproduction

```sh
./build/tclass.exe        # emit dataset from the production path
python build/tfeat.py     # feature audit: confirms no label/order leakage
python build/tablate.py   # ablation with cross-validation
python build/tclass.py    # headline classifier
python build/tclass2.py   # payload-size isolation
```

## Methodological notes

- The classifier receives only features derived from `t_ms`/`bytes`/`dir`. The
  class label and the trial index are never features (verified, `tfeat.py`).
- An earlier single-split run reported 74.2% and appeared to separate LARGE
  from SMALL. That separation was noise: every LARGE-vs-SMALL feature has
  Cohen's d < 0.2. Cross-validation and the payload-size isolation both put it
  at chance.

## Next steps — do not jump to maximum padding

1. Rerun under realistic network noise (jitter, variable RTT, Tor circuit
   variability) to see whether the finding survives.
2. Extend the adversary to real protocol states (handshake, rekey, close,
   reconnect) and to sequences, not single sessions.
3. Only then trial defences, smallest first, since the target is **frame
   count** rather than padding: transmission-schedule normalisation, then
   batching, then cover traffic.
4. Measure each defence against bandwidth, latency p50/p95/p99 and CPU. The
   goal is minimum observer advantage at acceptable cost — not driving
   accuracy to 25% with unbounded cover traffic.
